# Phase 2 — Execution-Plan Comparison (ef=10 vs ef=50)

**Evidence source:** live PostgreSQL 18.0 / pgvector 0.8.7, database `knn_knn_platform`  
**Audited commit:** `3dd6299` on `phase1-stabilization`  
**Read-only:** no dataset, experiment, index, schema or historical result was modified

## 1. Controlled comparison setup

| Item | Value |
|---|---|
| Training table | `fv_846` (derived from parent 116), 1,000 rows |
| Query table / vector | `tv_846`, `id=24`, 54-dim L2 vector from the shared 40-query set |
| SQL shape | `SELECT id, label, embedding <-> %s AS distance FROM "fv_846" ORDER BY embedding <-> %s LIMIT 5` |
| Plan statements | `EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)` and `EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, FORMAT TEXT)` on the same connection |
| Change between runs | only `hnsw.ef_search`, set with `SET` on the executing connection and confirmed by `SHOW` |
| Planner mode | natural: `enable_seqscan=on`, `enable_indexscan=on`, no forced GUCs |

The SQL shape used for EXPLAIN is generated by the application's own `_explain_sql()` helper and differs from the timed retrieval only by the EXPLAIN wrapper. The three smoke experiments used the identical 40-query id set.

## 7. Natural sweep and forced-mode proof

### Natural planner, 1,000-row pool

| ef_search | access path | top-node cost |
|---|---|---|
| 10 | HNSW index scan | `Limit  (cost=44.08..46.15 rows=5 width=26)` |
| 20 | HNSW index scan | `Limit  (cost=67.27..69.23 rows=5 width=26)` |
| 25 | Seq Scan | `Limit  (cost=75.61..75.62 rows=5 width=26)` |
| 30 | Seq Scan | `Limit  (cost=75.61..75.62 rows=5 width=26)` |
| 40 | Seq Scan | `Limit  (cost=75.61..75.62 rows=5 width=26)` |
| 50 | Seq Scan | `Limit  (cost=75.61..75.62 rows=5 width=26)` |
| 75 | Seq Scan | `Limit  (cost=75.61..75.62 rows=5 width=26)` |
| 100 | Seq Scan | `Limit  (cost=75.61..75.62 rows=5 width=26)` |
| 200 | Seq Scan | `Limit  (cost=75.61..75.62 rows=5 width=26)` |

Crossover: ef=10/20 use the index; ef>=25 use the sequential scan. Sequential plan cost is constant at 75.61.

### Forced HNSW (explicit transaction, `SET LOCAL enable_seqscan=off`, rolled back)

| ef_search | Limit node cost with forced HNSW |
|---|---|
| 10 | `Limit  (cost=44.08..46.15 rows=5 width=26)` |
| 50 | `Limit  (cost=127.96..129.61 rows=5 width=26)` |
| 100 | `Limit  (cost=217.83..219.03 rows=5 width=26)` |
| 200 | `Limit  (cost=267.50..268.45 rows=5 width=26)` |

At ef=50 the index startup cost (127.96) exceeds the natural sequential plan cost (75.61). The planner is not overlooking the index; it is choosing the cheaper path.

## 8. Interpretation

pgvector 0.8.7 prices HNSW search effort into the index cost. At 1,000 rows the exhaustive scan is cheap and flat, so raising ef from 20 to 25 flips the planner to a sequential scan. This is a planner economics issue, not a broken index, SQL incompatibility or connection-setting leak. It must not be "fixed" by relabelling experiment 383: its latency belongs to a sequential scan. The minimal safe change is to mark such runs `failed`, retain their plans and measured data as diagnostics, and exclude them from valid scientific summaries.

No conclusion is drawn about 5,000/10,000/20,000-row pools: no such indexed pools existed for read-only inspection. The 50,000-row result is supporting evidence only.
