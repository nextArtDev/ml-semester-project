### Three distinct levels — not interchangeable samples

1. **Individual query latency observations** (3,000 per experiment): the raw
   per-query timings. They describe this warm-cache workload, not a population
   sample; the 3,000 queries are the whole held-out pool, not repeated draws.
2. **Repetitions** (3 per experiment): complete passes over the *same* 3,000
   queries in the *same* order. They measure run-to-run timing variability
   (scheduler, buffer state, traversal), not sampling error.
3. **Benchmark rounds** (3 per pool): permutations of the configuration order.
   They change which configuration runs early or late, but neither the queries
   nor the index. Rounds are pairing for order fairness, not independent
   replicates of the system.

Totals: `2 sizes × 7 configurations × 3 rounds = 42` experiments;
`42 × 3 × 3,000 = 378,000` latency observations; 126 repetition rows;
420 repetition-summary rows.

## Balanced execution order

Each round contains all seven configurations exactly once. A seed picks a base
permutation; round *r* rotates it by `floor(7 / 3) = 2` positions. Exhaustive
tests verify that, for this supported 7×3 matrix, every configuration occupies
three distinct positions, every position is occupied by three different
configurations, and every configuration has both early and late slots. No
perfect balance is claimed for arbitrary matrix sizes.

| Configuration | Round 1 | Round 2 | Round 3 |
| --- | --- | --- | --- |
| exact | 4 | 2 | 7 |
| HNSW ef=10 | 3 | 1 | 6 |
| HNSW ef=25 | 2 | 7 | 5 |
| HNSW ef=50 | 6 | 4 | 2 |
| HNSW ef=100 | 1 | 6 | 4 |
| HNSW ef=200 | 5 | 3 | 1 |
| HNSW ef=400 | 7 | 5 | 3 |

The complete orders, seeds, actual pool sizes and experiment ids are in
`benchmark_orders.json`. Speed-ups use the mean exact baseline over the three
rounds, so they do not depend on which run preceded a configuration. The HNSW
index was built once per pool and reused across all ef values and rounds.

field is an HTTP/API latency measurement.

### Ground-truth cache

The exact ground-truth neighbours depend only on pool fingerprint, query ids,
k, metric and tie tolerance. A bounded in-process cache keyed on those values
was computed on the first run of each pool and reused on the other 20 runs per
pool (2 misses / 40 hits). It is computed before retrieval, so per-query
latency is unaffected. Each row records `ground_truth_cache_hit` and the lookup
time; disabling it via `use_ground_truth_cache=False` recomputes the same
ground truth with identical recall and accuracy (covered by a test).

## Interpretation and limitations

* **Sampling effect removed.** All 3,000 held-out rows were evaluated, so the
  query-composition difference from v1/v2 is no longer confounded with method.
* **Order effect controlled, cache effect not.** Balanced rounds remove the
  fixed exact-first confound, but all measurements are warm-cache.
* **Correct levels of variability.** The ± values are between-round variation
  in p50, not confidence intervals. Repetitions and rounds are correlated with
  the same queries and index.
* **Retrieval versus classification.** Recall@5 spans 0.9854–1.0000 while
  accuracy differs from exact by at most 0.17 pp here. This asymmetry is a
  property of `k = 5` majority voting on this workload, not a general law.
* **Index cost is one-off but real.** Build time and 5–25 MiB of storage are
  reported separately from query latency.
* **Scope.** One dataset, one metric in the full sweep, warm localhost cache,
  per-query round-trip. No claim is made that these Covertype speed-ups apply
  to every dataset.
